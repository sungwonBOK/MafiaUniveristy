# DOMAIN 문서

## 네트워크 동기화와 서버 틱 배치

### 배경
- 기존 구조는 `PLAYER_MOVE` 수신마다 즉시 브로드캐스트를 수행했습니다.
- 동시 이동이 많아지면 이벤트 수가 늘고 서버 CPU와 소켓 송신 호출이 빠르게 증가합니다.

### 현재 구조
- `Room`은 플레이어별 최신 좌표를 `pendingPlayerStates` 큐(`Map`)에 적재합니다.
- 서버는 고정 틱(`SERVER_TICK_RATE`, 기본 20Hz)으로 각 방 큐를 비웁니다.
- 같은 틱 안에서 같은 플레이어가 여러 번 이동해도 최신 좌표 1개만 유지됩니다.
- 브로드캐스트는 `io.to(room.id).except(playerId)`로 송신자 제외 전파를 사용합니다.

### 왜 이 방식인가
- 이동 동기화에서 중요한 것은 "중간 경로 전체"가 아니라 "짧은 주기별 최신 상태"입니다.
- 즉시 전송 대신 배치를 적용하면 호출 수가 줄어 서버 병목이 완화됩니다.
- 큐를 `Map<playerId, state>`로 두어 중복 입력을 자연스럽게 압축할 수 있습니다.

### 트레이드오프
- 틱 기반 구조는 최대 `1 / tickRate`만큼의 전송 지연을 가집니다. 20Hz 기준 약 50ms입니다.
- 대신 대규모 입력 구간에서 안정성과 확장성이 더 좋아집니다.

### 운영 파라미터
- `SERVER_TICK_RATE`: 서버 배치 틱 기본값 20
  - 권장 범위: 20~30
  - 너무 낮으면 움직임이 둔해지고 너무 높으면 CPU 이득이 줄어듭니다.

### 2026-03 테스트 메모
- 기본 틱을 `24Hz`로 상향했습니다.
- 운영 중 과도한 값으로 서버 부하가 커지지 않도록 `SERVER_TICK_RATE`는 `15~30` 범위로만 조율합니다.
- 클라이언트 `SEND_INTERVAL`은 `40ms`로 조정해 반응성을 올리고 원격 보간은 거리 기반 계수(`0.20~0.30`)를 적용했습니다.

## 직렬화에 MessagePack 적용

### 배경
- 이동 이벤트 빈도가 높아 JSON 문자열 직렬화 오버헤드가 누적됩니다.

### 현재 구조
- 서버 `Socket.IO Server`와 클라이언트 `socket.io-client` 모두 `socket.io-msgpack-parser`를 사용합니다.
- 동일 이벤트 구조를 유지한 채 전송 포맷만 MessagePack으로 교체합니다.

### 기대 효과
- 페이로드 크기와 직렬화 비용이 감소해 대역폭 사용량이 줄어듭니다.
- 게임 로직 변경 없이 네트워크 계층에서만 최적화할 수 있습니다.

## 학교별 맵 생성 구조

### 배경
- 홈 화면에서 사용자가 학교를 선택하므로, 게임 씬도 같은 학교 값에 따라 다른 맵을 제공해야 합니다.
- 하지만 초기 단계에서는 학교별 타일맵 에셋이 아직 없을 수 있으므로, 에셋 부재 때문에 게임 진입이 막히면 안 됩니다.

### 현재 구조
- `SchoolMapRegistry`가 학교별 맵 설정의 단일 진입점입니다.
- 설정에는 맵 키, 월드 크기, 스폰 위치, 타일맵 키가 포함됩니다.
- `PreloadScene`은 선택된 학교에 해당하는 타일맵 경로만 로딩 시도합니다.
- 실제 에셋이 없으면 `GameScene`은 절차적 맵 생성기로 자동 전환합니다.

### 왜 이 구조인가
- 학교 추가 시 레지스트리에 한 줄을 더하고 학교별 레이아웃 파일 하나를 추가하면 됩니다.
- 학교 수가 많아져도 모든 맵을 한 파일에 몰아넣지 않아 SRP를 지킬 수 있습니다.
- 나중에 OSM 전처리 결과물, 수동 제작 타일맵, 혼합 방식으로 바꾸더라도 씬 진입 구조는 유지됩니다.

### 확장 원칙
- 공통 정책은 `SchoolMapRegistry`와 `procedural/helpers.ts`에 둡니다.
- 학교별 차이는 `procedural/layouts/<school>Layout.ts` 파일에만 둡니다.
- 외부 데이터 연동이 시작되더라도 학교별 데이터 적재기 역시 같은 분리 원칙을 유지합니다.

## 서버 주도 투표 흐름

### 배경
- 투표는 `VOTE_RESULT` 한 번만 보내는 것으로 끝나지 않습니다.
- 회의가 시작되면 누가 이미 투표했는지, 언제 자동 종료되는지, 언제 모달을 닫아야 하는지가 같은 기준으로 움직여야 합니다.
- 이 상태를 클라이언트 로컬 상태에만 맡기면 화면마다 시간이 어긋나거나 회의 종료 시점이 달라질 수 있습니다.

### 현재 구조
- 서버가 방 단위 투표 상태를 관리합니다.
- 회의 시작 시 서버가 투표 마감 시각(`deadlineAt`)과 유효 투표 인원 수를 확정합니다.
- 각 투표가 들어올 때마다 서버가 `VOTE_PROGRESS`를 브로드캐스트해서 투표 완료 플레이어 목록과 진행 수치를 갱신합니다.
- 60초가 지나거나 생존자가 모두 투표하면 서버가 즉시 집계를 끝내고 `VOTE_RESULT` 또는 `GAME_ENDED`로 회의를 종료합니다.

### 왜 이 구조인가
- 투표 종료 조건이 한 곳에 있어야 제한시간 자동 스킵과 전체 진행이 일관됩니다.
- 클라이언트는 서버가 보낸 상태를 렌더링만 하면 되므로, 모달 UI와 실제 게임 상태가 어긋날 가능성이 줄어듭니다.
- 이후 재연결 복구, 역할별 투표 예외, 투표 로그 표시가 추가돼도 서버 상태만 확장하면 됩니다.

## 역할/진영 아키텍처 기초 정리 (2026-03-11)

### 배경
- 기존 코드는 역할 문자열(`mafia`, `citizen`)을 서버/클라이언트 여러 곳에서 직접 비교했습니다.
- 이 방식은 역할이 늘어날수록 분기 코드가 급격히 늘고, 한 역할을 바꾸면 여러 파일을 동시에 수정해야 합니다.
- 특히 출석 대리인(변신) 역할은 "실제 신원"과 "화면 표시 신원"을 분리하지 않으면 나중에 큰 리팩터링이 필요합니다.

### 이번에 반영한 구조
- `shared`에 `ROLE_META`와 `Faction`을 추가해 역할별 진영 정보를 단일 기준점으로 관리합니다.
- 서버 승리 판정은 이제 특정 문자열 비교 대신 진영(`professor` vs 나머지) 기반으로 계산합니다.
- 서버 `Player`는 `realNickname/realColor`와 `displayNickname/displayColor`를 분리해 보관합니다.
- 클라이언트 렌더링은 `displayNickname`, `displayColor`를 우선 사용하도록 맞췄습니다.

### 왜 이 순서인가
- 스킬 구현보다 먼저 "역할 데이터 구조"를 고정해야 이후 기능이 누적돼도 수정 범위가 작아집니다.
- 승리 판정, 역할 표시, 능력 실행 권한을 같은 메타 기준으로 묶으면 하드코딩 분기가 줄어듭니다.
- 지금 구조를 먼저 잡아두면 2단계 스킬 구현(`investigator`, `topstudent`, `freshman`)과 3단계 변신 구현(`impersonator`)에서 충돌을 줄일 수 있습니다.
