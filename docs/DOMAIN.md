# DOMAIN 문서

## 네트워크 동기화: 서버 틱 배칭

### 배경
- 기존 구조는 `PLAYER_MOVE` 수신마다 즉시 브로드캐스트를 수행했습니다.
- 동시 이동이 많아지면 이벤트 폭주로 서버 CPU와 소켓 송신 호출 수가 빠르게 증가합니다.

### 현재 설계
- `Room`은 플레이어별 최신 좌표를 `pendingPlayerStates` 큐(`Map`)에 적재합니다.
- 서버는 고정 틱(`SERVER_TICK_RATE`, 기본 20Hz)으로 각 방 큐를 비웁니다.
- 같은 틱에서 한 플레이어가 여러 번 이동해도 **최신 좌표 1개만** 유지됩니다.
- 브로드캐스트는 `io.to(room.id).except(playerId)`로 송신자 제외 전파합니다.

### 왜 이 방식인가
- 이동 동기화에서 중요한 것은 "중간 경로 전부"가 아니라 "짧은 주기의 최신 상태"입니다.
- 즉시 전송 대신 틱 배칭을 적용하면 호출 수가 줄어 서버 병목을 완화할 수 있습니다.
- 큐를 `Map<playerId, state>`로 두어 중복 입력을 자연스럽게 압축할 수 있습니다.

### 트레이드오프
- 틱 기반 구조는 최대 `1 / tickRate`만큼의 전송 지연(예: 20Hz 기준 약 50ms)을 가질 수 있습니다.
- 대신 대규모 입력 구간에서 안정성과 일관성이 크게 좋아집니다.

### 운영 파라미터
- `SERVER_TICK_RATE`: 서버 배칭 틱(기본값 20)
  - 권장 범위: 20~30
  - 너무 낮으면 움직임이 둔해지고, 너무 높으면 CPU 이득이 줄어듭니다.

### 2026-03 튜닝 메모
- 기본 틱은 `24Hz`로 상향했습니다.
- 운영 중 과도한 값으로 서버 부하가 커지지 않도록 `SERVER_TICK_RATE`는 `15~30` 범위로 클램프합니다.
- 클라이언트 `SEND_INTERVAL`은 `40ms`로 조정해 반응성을 올렸고, 원격 보간은 거리 기반 계수(`0.20~0.30`)를 적용했습니다.

## 직렬화: MessagePack 적용

### 배경
- 이동 패킷은 빈도가 높아 JSON 문자열 직렬화 오버헤드가 누적됩니다.

### 현재 설계
- 서버 `Socket.IO Server`와 클라이언트 `socket.io-client` 모두 동일한 `socket.io-msgpack-parser`를 사용합니다.
- 동일 이벤트 구조를 유지한 채 전송 포맷만 MessagePack으로 교체합니다.

### 기대 효과
- 패킷 크기와 직렬화 비용이 감소하여 대역폭 사용량이 줄어듭니다.
- 게임 로직 변경 없이 네트워크 계층에서만 최적화됩니다.
